## 2. 법칙 (표본 6편 기준 — 4편 이상 일치한 것만)

### ① 문단은 **한 호흡**으로 끊는다 — 최대 26~31자

중간값 8~16자, p75 14~22자, 최대 26~31자(한 편만 84). 모바일 화면에서
**한 줄~두 줄**로 끝난다. 스크롤이 리듬을 타고, 눈이 쉴 자리가 계속 생긴다.

> 우리 현재 출력은 60~80자다. **3배 길다.** 이게 "가독성 최악" 의 실체다.

### ② 사진 밀도 — **글자 100자당 사진 1장**

76 / 93 / 103 / 128 / 193 / 217 자per장. **중앙값 약 100.** 본문 2,000자면 사진 20장.

> 티스토리 영상 글에서 얻은 "100자당 1장" 과 같은 숫자다 (HANDOVER 7-1).
> 플랫폼이 달라도 사람이 읽는 방식은 같다는 뜻으로 읽힌다.

### ③ 소제목(`sectionTitle`)을 **거의 쓰지 않는다** — 6편 중 5편이 0개

구조를 만드는 건 소제목이 아니라 **인용구 + 구분선**이다.

> ⚠️ 다만 **그대로 따라가면 안 된다.** 소제목이 0개면 검색엔진과 AI 답변이
> 글의 목차를 잡지 못한다. → 우리 정체성 절(3장)에서 절충한다.

### ④ 인용구가 구조의 주역 — 6~23개, 종류를 섞는다

관찰된 종류: `default` · `quotation_line` · `quotation_bubble` ·
`quotation_underline` · `quotation_postit`. 한 글에서 2~4종을 섞어 쓴다.
길이는 대개 10~40자 — **짧은 한마디**를 세우는 용도다.

### ⑤ `placesMap`(장소 첨부)은 **거의 필수** — 6편 중 5편 사용 (1~5개)

여행 글에서 이것이 없으면 네이버 지역 검색·지도 연계에서 밀린다.
장소가 여러 곳이면 **장소마다 하나씩** 넣는다 (jwsu73 는 5개).

> **아직 구현하지 않았다.** 스키마 실측이 필요하다 (다음 작업 후보 1순위).

### ⑥ 구분선으로 단락을 끊는다 — 1~23개

소제목 대신 시각적 구분을 만드는 수단. 장소가 바뀌는 지점, 화제가 바뀌는 지점.

### ⑦ 기본 리듬은 `사진 → 짧은 글 → 사진 → 짧은 글`

텍스트 뒤에 항상 사진이 오고, 사진 뒤에 항상 짧은 글이 온다.
중간중간 `구분선 → 인용구` 로 호흡을 끊는다.

### ⑧ 이미지 캡션을 거의 쓰지 않는다 (0~3개)

사진 아래 설명 대신 **다음 문단**이 그 역할을 한다.

### ⑨ ~~콜라주(`imageGroup`)를 아무도 쓰지 않았다~~ → **틀렸다. 측정 버그였다**

> 🔴 **2026-07-29 정정.** `scripts/bench-naver.mjs` 의 `kindOf` 정규식이
> `image|imageGroup` 순서로 되어 있어 **`se-imageGroup` 이 `image` 로 잡혔다.**
> "6편 모두 0개" 는 도구가 만든 착각이다. 순서를 고쳐(`imageGroup` 을 앞으로)
> 다시 재니 우리 발행글의 콜라주 4개가 그대로 보였다.
>
> 검색 상위 8편을 새로 측정한 결과 **3편이 콜라주를 쓴다** —
> sanghan1990 9개 · radiant0_0_ 6개 · ppororogo 2개.

옳은 규칙: **연관 있는 두 컷만 묶는다.** 같은 공간의 가로/세로, 같은 야경 두 컷처럼
나란히 놓아야 의미가 사는 쌍이다. 관계없는 두 장을 붙이면 둘 다 죽는다.
→ 구현은 `imageBriefs[].group` (같은 값이면 한 묶음). 자동 1·2·2·1 리듬은 관계를
모르므로 여행 글에서는 쓰지 않는다 (`naver.collage: false`).

### ⑩ 표는 절반이 쓴다 (0~8개) — 팩트 정리용

주소·영업시간·요금처럼 **눈으로 스캔하는 정보**에만 쓴다. 서술에는 안 쓴다.

## 3. 우리 정체성 — 참고 글을 그대로 베끼지 않는 지점

참고 글은 **읽는 리듬**을 배울 대상이고, **SEO/GEO 체계는 우리가 세운다.**

| 항목 | 참고 글 | **우리 방식** | 이유 |
|---|---|---|---|
| 소제목 | 0개 | **섹션마다 `sectionTitle`** | 검색엔진 목차·AI 답변 인용의 근거. 없으면 GEO 를 포기하는 것 |
| 문단 길이 | 8~31자 | **25~40자** | 참고 글보다 약간 길게. 정보 밀도를 지키면서 호흡은 살린다 |
| 사진 밀도 | 100자/장 | **100자/장** | 그대로 따른다. 근거가 4편에서 일치한다 |
| 인용구 | 구조 대용 | **역할 고정** | 결론=`_line` / 팁=`_postit` / 인물·후기=`_bubble`. 독자가 모양으로 역할을 안다 |
| 한 줄 정리 | 없음 | **맨 위에 배치** | GEO 핵심. AI 가 인용할 한 문장을 글 맨 앞에 둔다 |
| FAQ | 없음 | **유지** | 롱테일 검색 유입 + AI 답변 인용 |
| 장소 | `placesMap` | **`placesMap` + 주소 표** | 지도(지역 SEO) 와 텍스트 주소(크롤링) 를 함께 |
| 스티커 | 3~6개 | **쓰지 않음** | 브랜드 톤과 안 맞고 정보 가치가 0 |

### 우리 글의 표준 순서 (호텔 + 근교 관광지)

```
대표 사진 (represent)
한 줄 정리            quotation_line   ← GEO: AI 가 인용할 한 문장
이 글의 핵심          sectionTitle + 가운뎃점 목록
─────────────────
[호텔]
  sectionTitle        "○○호텔 — 위치·객실·조식 한눈에"
  사진 → 짧은 글 → 사진 → 짧은 글 …
  quotation_postit    실제로 묵어 본 팁 / 주의
  표                  주소·체크인·요금·조식 시간
  placesMap           호텔 위치
─────────────────
[근교 관광지 N곳]  ← 호텔에서의 이동 시간을 반드시 함께 쓴다
  sectionTitle        "호텔에서 15분 — ○○"
  사진 → 짧은 글 → 사진 → 짧은 글 …
  quotation_bubble    현장에서 느낀 한마디
  표                  입장료·영업시간·소요 시간
  placesMap           관광지 위치
─────────────────
동선 정리             sectionTitle + 시간순 목록  ← "1일 코스" 검색 대응
예산 정리             sectionTitle + 표
자주 묻는 질문        sectionTitle + Q/A
마치며
─────────────────
참고 자료 · 이미지 출처
```

**호텔 + 근교를 엮는 것이 차별점이다.** 호텔 리뷰만 쓰는 글, 관광지만 쓰는 글은
넘친다. "이 호텔에 묶으면 근처에 뭐가 있나" 를 한 글에서 해결해 주는 것이
우리 글의 존재 이유다. → 관광지 섹션 제목에 **호텔로부터의 이동 시간**을 넣는다.

## 4. 기술 메모 — 실측으로만 알 수 있었던 것

### 제로폭 공백으로 여백을 만든다

문단 길이 분포에서 **최소·중간값이 1** 인 것의 정체는 빈 문단이 아니라
**제로폭 공백(`​`) 한 글자가 든 문단**이다.

> 빈 문단(`value: ''`)은 **발행하면 삭제된다** (실측: 발행된 글의 빈 문단 0개).
> 제로폭 공백을 넣으면 살아남아 한 줄 여백이 된다. 표본 6편이 모두 이 방법을 쓴다.

문단 사이를 띄우는 다른 방법은 전부 막혀 있었다:

| 시도 | 결과 |
|---|---|
| 빈 문단 | 발행 시 삭제 |
| 문단마다 컴포넌트 분리 | 인접 컴포넌트 간격 **0px** |
| 줄간격 `paragraphStyle.lineHeight` | **동작** (발행된 글에 `style="line-height:2.0;"`) |
| **제로폭 공백 문단** | **동작** (참고 글 6편이 모두 이 방법을 쓴다) |

### 참고 글의 타이포그래피

- 본문 15px 이 기본, 한 편만 19px(`se-fs-fs19`)
- 줄간격은 대부분 지정하지 않고(계산값 19.8px), 한 편만 `line-height:1.9`
- 즉 **줄간격보다 문단을 짧게 끊는 것이 본질**이다. 우리가 2.0 으로 올린 것은
  보조 수단이고, 문단 길이를 25~40자로 줄이는 것이 진짜 해결이다

### 여백 문단 — **검증 완료**

한때 `spacedParagraphs([para])` 로 **문단 하나씩** 넘기는 바람에 배열 길이가 항상 1 이어서
여백이 한 번도 삽입되지 않았다 (발행글 실측: 여백 문단 0개).
"문단들 사이" 여백은 호출 단위가 하나면 만들 수 없다 — 당연한데 놓쳤다.

고친 뒤 발행해 확인: **제로폭 공백 문단 14개가 살아남았다** (0 → 14).
가운데 정렬도 177개 중 163개 적용, 문단 길이 median 25 / p75 29 유지.

### 사진 — 로컬 폴더가 스톡을 대체한다 (2026-07-28 구현·실측)

법칙 ②(100자당 1장)와 ⑨(콜라주 0개)를 코드에 박았다. 자세한 내용은
`references/laqua-embeds.md` 의 '자동화' 절.

| 항목 | 전 | 후 |
|---|---|---|
| 사진 출처 | 스톡 검색(그 장소가 아닌 사진) | **눈으로 고른 로컬 폴더** (`article.photoDir`) |
| 본문 사진 수 | `images.bodyImages` = 5 로 잘림 | `article.bodyImageCount` = imageBriefs 개수 (15) |
| 콜라주 | 1·2·2·1 리듬 | `naver.collage: false` → **한 장씩** |
| 배치 | 프리뷰가 섹션에 고르게 추정 | **아티클의 `afterSection` 그대로** |
| 비율 | 대표는 정사각 크롭 | 로컬 사진은 **원본 비율** (간판이 잘리면 증명이 사라진다) |

배운 것: **사진이 글의 구조를 정한다.** 초안의 `photoQuery` 는 "고라쿠엔역 입구",
"카드 결제 단말기" 같은 스톡용 지시였는데 실제 가진 컷과 하나도 맞지 않았다.

## 7. `placesMap`(장소) — 진행 중 (2026-07-28)

### ⚠️ 해외 장소는 **'해외' 로 바꿔야 검색된다**

`장소` 버튼(`button.se-map-toolbar-button`)을 누르면 지도 레이어가 열린다.
검색창 **왼쪽에 `국내` / 해외 선택 드롭다운**이 있고 **기본값이 `국내`** 다.

> 2026-07-28 실측: 검색어 "도쿄돔시티" 를 넣었더니 **"검색 결과가 없습니다"**.
> 검색어가 틀린 게 아니라 필터가 `국내` 였다.

**"어디가지?" 는 전 세계를 다루므로 이게 치명적이다.** 이 드롭다운을 바꾸지 않으면
해외 글마다 장소가 조용히 0개가 되고, 실패 원인이 "검색어가 나쁘다" 로 오진된다.

→ 구현할 때 **국가/지역에 따라 국내·해외를 먼저 고른 뒤** 검색해야 한다.
   아티클에 '해외인가' 를 알려주는 값이 필요하다 (프롬프트에서 받거나 좌표로 판단).

### 레이어 구성 (실측)

| 요소 | 위치·역할 |
|---|---|
| 국내/해외 선택 | 검색창 왼쪽 드롭다운. **기본 `국내`** |
| 검색 입력 | 검색창. `Enter` 로 검색 |
| 결과 목록 | 왼쪽 패널 (없으면 "검색 결과가 없습니다") |
| `지도에 직접 표시` | 좌하단. 검색으로 안 잡히는 곳을 좌표로 찍는 폴백 |
| `확인` | 우하단. 선택을 확정해 본문에 삽입 |

### 다음 단계

1. 국내/해외 드롭다운의 셀렉터를 뜬다
2. '해외' 로 바꿔 다시 검색 → 결과 클릭 → `확인`
3. `getDocumentData()` 로 `placesMap` 컴포넌트 JSON 확보
4. 확보하면 `naverDoc.js` 에 `placesMap()` 빌더를 추가하고,
   호텔·관광지 섹션마다 하나씩 넣는다 (표본 jwsu73 은 5개)

⚠️ 사진 업로드처럼 **커서 위치에 삽입되는 컴포넌트**일 가능성이 크다.
그렇다면 사진과 마찬가지로 **본문 주입 전에 미리 삽입해 JSON 을 회수**하고,
조립 단계에서 원하는 자리에 끼우는 방식이 맞다 (naver.js 의 uploadImages 와 같은 전략).

### 결정: **국내만 쓰고, 없으면 넣지 않는다** (2026-07-28, 사용자 결정)

해외 장소는 `placesMap` 을 쓰지 않는다. 국내/해외 드롭다운을 다룰 필요가 없어진다.
확보되지 않으면 비운다 — 프로젝트 원칙("확실하지 않으면 넣지 않는다")과 같다.

→ 구현 시 아티클이 국내인지 판단해 국내일 때만 시도하고, 실패하면 조용히 건너뛴다.
   해외 글은 대신 **주소를 텍스트로** 남긴다(크롤링 대상이 되므로 SEO 효과는 유지).

### 삽입은 **2단계**다 — 결과 `추가` → `확인`

> 2026-07-28 실측: "제주 성산일출봉" 으로 검색해 결과를 정확히 찾았고
> (`성산일출봉 제주특별자치도 서귀포시 성산읍 성산리 1 추가`) `확인` 까지 눌렀지만
> **컴포넌트가 생기지 않았다** (documentTitle, text 만 남음).

결과 항목 텍스트 끝의 **`추가`** 가 단서다. 결과 목록에서 항목을 클릭하는 것으로는
선택되지 않고, **항목 안의 `추가` 버튼**을 눌러 담아야 한다(여러 곳을 담을 수 있다).
그다음 `확인` 이 담긴 목록을 본문에 삽입한다.

### 스키마 — **확보 완료** (2026-07-28)

셀렉터:

| 대상 | 셀렉터 |
|---|---|
| 장소 버튼 | `button.se-map-toolbar-button` |
| 검색 입력 | 레이어 안 `input[type=text]` 첫 번째 |
| 결과 항목 | `li.se-place-map-search-result-item` |
| 결과 링크 | `a.se-place-map-search-result-link` |
| **추가** | **`button.se-place-add-button`** |
| 확정 | `button:has-text("확인")` |

⚠️ 결과 항목(`li`)이나 링크(`a`)를 클릭하면 **담기지 않는다.** 항목 안의
`button.se-place-add-button` 을 눌러야 목록에 담긴다. 여러 곳을 담고 한 번에 `확인`.

  "layout": "default",
  "searchEngine": "naver",
  "thumbnail": {
    "src": "https://simg.pstatic.net/static.map/v2/map/staticmap.bin?caller=smarteditor&markers=…&w=700&h=315&scale=2&dataversion=178.08",

  },

(place 노드의 `@ctype` 은 `place` 다)

**우리가 만들어 낼 수 없다.**

→ 그래서 **사진과 같은 전략**을 쓴다: 본문 주입 전에 UI 로 장소를 삽입해
   `placesMap` 컴포넌트를 회수하고, 조립 단계에서 원하는 자리에 끼운다
   (`naver.js` 의 `uploadImages` 와 같은 구조).
   장소 이름은 codex 가 아티클에 담아 줘야 한다 (프롬프트 작업과 함께).

### 이것이 뜻하는 것

`mobileLines()` 로 문단을 사후에 쪼갠 것은 **②만 흉내 낸 것**이다.
①③④⑤⑥⑦⑧ 은 전부 **프롬프트가 만들어야 한다.** 코드로는 못 만든다.

특히 ⑥ 이 중요하다 — 구어체로 쓰면서도 **사실은 출처를 밝혀** 신뢰를 만든다.
"다녀온 것처럼" 이 통하는 이유가 감상 때문이 아니라 **정보가 정확해서**다.
우리가 검색으로 확인한 사실(요금·영업시간·동선)을 문장 안에서 근거와 함께 쓰면
같은 효과가 난다.

### ⚠️ 현지인 전용 정보를 실으면 섹션이 통째로 죽는다

> 실측 — 스파 라쿠아 초안의 7개 섹션 중 하나가
> **`8월 d포인트 5배, 실제 조건은 무엇인가`** 였다.
> `d포인트`는 NTT 도코모 포인트다. **한국 여행자는 적립도 사용도 못 한다.**
> 섹션 하나(본문 700자 + 사진 2장)가 통째로 무용지물이 됐다.
>
> 사진 검색어에도 `mobile payment card store`, `smartphone travel schedule` 이
> 들어가 있었다 — 일본 결제앱 화면을 찾으라는 지시였다.

원인: 프롬프트가 **원문에 있는 정보를 중요도순으로 옮기라**고만 지시한다.

### 사진 배치 규칙 (문장 법칙 ②와 함께)

시안 글의 흐름을 그대로 옮기면:

```
사진 → 짧은 글 2~3줄 → 사진 → 짧은 글 2~3줄 → …
        중간중간 구분선 → 인용구(팁)
```

- 사진 **한 장씩** 세운다 (표본 6편 모두 콜라주 0개 — 법칙 ⑨)
- 사진 뒤에는 **반드시 그 사진을 잇는 문장**이 온다. 캡션 대신 다음 문단이 설명한다
- 밀도는 **본문 100자당 1장** (법칙 ②)
- 순서는 **실제 동선** — 도착 → 입구 → 접수 → 시설 → 식사 → 나오는 길.
  정보 중요도순이 아니다. 따라 걷는 느낌이 나야 한다

### 사진 색보정(룩) — 여행 글은 후지 계열 (2026-07-28)

`config.json → images.look` 하나로 갈아 끼운다. 비교: `node scripts/look-compare.mjs <사진…>`

| 룩 | 성격 | 언제 |
|---|---|---|
| `canon` | 따뜻·고채도 (기존 기본) | 연예·이슈 글 |
| `fuji` | 클래식크롬 — **저채도·고콘트라스트**, 그림자에 청록 | 정보 위주 여행 글 |
| `fujiSoft` | **감성·에어리** — 콘트라스트 낮추고 블랙을 들어 올려 뽀얗게 | 감성 여행 글 |
| `velvia` | 풍경 고채도 — 야경·조명·물색이 산다 | 야경 중심 글 (인물엔 금지) |
| `eterna` | 시네마 평탄 — 출처가 섞인 사진을 묶을 때 | 사진 톤이 제각각일 때 |

실측에서 배운 것:

- **필름 톤의 정체는 채도가 아니라 들린 블랙(faded black)** 이다. CSS `filter` 로는
  만들 수 없다 (`brightness` 는 사진 전체를 밝힌다). `mix-blend-mode:screen` 오버레이가
  **어두운 픽셀만** 밀어 올린다 — 이게 실제 장치다
- 같은 룩이 사진에 따라 **정반대로 작동한다.** `fujiSoft` 는 야경·파스텔에서 감성이
  되지만 이미 밝은 주간 사진에서는 그냥 흐려진다. 이름으로 고르지 말고 **쓸 사진으로** 비교한다
- 룩은 본문 사진 + 카드에 모두 걸리지만, **흑백 레이아웃(`neon`·`magazine`)은 제외**한다.
  `grayscale(1)` 뒤에 `sepia` 를 붙이면 색이 되살아나 갈변한다 (실측)
- 오버레이는 **본문 사진 전용**이다. 카드에는 스크림·글자가 이미 얹혀 있어
  한 겹 더 깔면 글자 대비가 무너진다

### 인스타 감성 룩 — 정체는 색이 아니라 소프트 글로우 (2026-07-28)

여성 독자가 "예쁘다" 고 느끼는 톤을 만들려고 색만 만졌더니 안 나왔다.
그 느낌의 실제 장치는 **소프트 글로우** — 밝은 부분이 은은하게 번지는 것이다.
보정 앱이 "예쁘게" 만들 때 쓰는 것이고, `saturate`·`brightness` 로는 재현되지 않는다.

구현: **사진을 한 겹 더 깔아 `blur` 로 흐리게 만든 뒤 `screen` 으로 얹는다.**
새 의존성 없이 렌더 CSS 안에서 끝난다 (`images.js` 의 `photoHtml`).

| 룩 | 성격 | 잘 맞는 사진 |
|---|---|---|
| `instaRosy` | 살구·핑크 파스텔 | 야간 조명·파스텔 카바나·수증기 |
| `instaAiry` | 민트·청량 | 수영장·유리·야경 |
| **`goldenHour`** | **해질녘 금빛 (사용자 선택 · 현재 기본)** | 창가·석양·조명등 |

`goldenHour` 를 라쿠아 24장 전부에 걸어 확인했다(2026-07-28). 걱정했던
"주간 사진이 누렇게 뜬다" 는 **이 세트에서는 일어나지 않았다** — 고라쿠엔역 주간
외경(위키미디어)도 하늘색이 그대로 남고 따뜻함만 얹혔다. 맑은 하늘 사진이라
색이 버텨 준 것이고, **흐린 날·형광등 실내 사진에서는 다시 봐야 한다.**

실측에서 배운 것:

- 글로우 레이어는 **사진보다 크게** 잡아야 한다. `blur(n)` 은 대략 `3n` 까지 퍼지므로
  여백을 `3n` 픽셀로 준다. 같은 크기로 흐리면 **테두리에 띠가 생겨 액자처럼 보인다.**
  퍼센트(`-4%`)로 주면 작은 사진에서 여백이 모자란다
- **처음 값은 과했다.** 평균 밝기를 `+40` 이나 올려 뿌옇게 날아갔다(101→141).
  `+20` 수준으로 낮추니 하이라이트 날아감이 **원본 이하**로 유지되면서 글로우는 남았다.
  기준: `contrast 0.96 · brightness 1.00 · 오버레이 0.10 · 글로우 0.16`
- **"밝은 사진에는 글로우를 줄인다" 는 자동 보정은 헛다리였다.** 원본 평균 밝기를
  재 보니 문제의 실내 사진이 오히려 어두웠다(100.7). 뿌예진 원인은 원본 밝기가 아니라
  **얹은 양**이었다. 눈으로 본 증상에 원인을 갖다 붙이지 말고 **재고 나서 고친다**
- 글로우·오버레이는 **본문 사진 전용**이다. 카드에 깔면 제목 글자 대비가 무너진다
