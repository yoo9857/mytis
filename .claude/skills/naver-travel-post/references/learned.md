## 2. 법칙 (표본 6편 기준 — 4편 이상 일치한 것만)

### ① 문단은 **한 호흡**으로 끊는다 — 최대 26~31자

중간값 8~16자, p75 14~22자, 최대 26~31자(한 편만 84). 모바일 화면에서
**한 줄~두 줄**로 끝난다. 스크롤이 리듬을 타고, 눈이 쉴 자리가 계속 생긴다.

> 우리 현재 출력은 60~80자다. **3배 길다.** 이게 "가독성 최악" 의 실체다.

### ② 사진 밀도 — **글자 100자당 사진 1장**

76 / 93 / 103 / 128 / 193 / 217 자per장. **중앙값 약 100.** 본문 2,000자면 사진 20장.

> 티스토리 영상 글에서 얻은 "100자당 1장" 과 같은 숫자다 (HANDOVER 7-1).
> 플랫폼이 달라도 사람이 읽는 방식은 같다는 뜻으로 읽힌다.

### ③ 소제목(`sectionTitle`)을 **거의 쓰지 않는다** — 6편 중 5편이 0개

구조를 만드는 건 소제목이 아니라 **인용구 + 구분선**이다.

> ⚠️ 다만 **그대로 따라가면 안 된다.** 소제목이 0개면 검색엔진과 AI 답변이
> 글의 목차를 잡지 못한다. → 우리 정체성 절(3장)에서 절충한다.

### ④ 인용구가 구조의 주역 — 6~23개, 종류를 섞는다

관찰된 종류: `default` · `quotation_line` · `quotation_bubble` ·
`quotation_underline` · `quotation_postit`. 한 글에서 2~4종을 섞어 쓴다.
길이는 대개 10~40자 — **짧은 한마디**를 세우는 용도다.

### ⑤ `placesMap`(장소 첨부)은 **거의 필수** — 6편 중 5편 사용 (1~5개)

여행 글에서 이것이 없으면 네이버 지역 검색·지도 연계에서 밀린다.
장소가 여러 곳이면 **장소마다 하나씩** 넣는다 (jwsu73 는 5개).

> **아직 구현하지 않았다.** 스키마 실측이 필요하다 (다음 작업 후보 1순위).

### ⑥ 구분선으로 단락을 끊는다 — 1~23개

소제목 대신 시각적 구분을 만드는 수단. 장소가 바뀌는 지점, 화제가 바뀌는 지점.

### ⑦ 기본 리듬은 `사진 → 짧은 글 → 사진 → 짧은 글`

텍스트 뒤에 항상 사진이 오고, 사진 뒤에 항상 짧은 글이 온다.
중간중간 `구분선 → 인용구` 로 호흡을 끊는다.

### ⑧ 이미지 캡션을 거의 쓰지 않는다 (0~3개)

사진 아래 설명 대신 **다음 문단**이 그 역할을 한다.

### ⑨ 콜라주(`imageGroup`)를 아무도 쓰지 않았다 — **6편 모두 0개**

사진을 2장 묶으면 각 사진이 작아진다. 여행 글에서 사진은 주인공이므로
**한 장씩 크게** 세운다. (우리가 넣은 1·2·2·1 리듬은 재미 요소로는 좋지만
여행 글에서는 **기본을 1장**으로 두고 예외적으로만 묶는 편이 맞다)

### ⑩ 표는 절반이 쓴다 (0~8개) — 팩트 정리용

주소·영업시간·요금처럼 **눈으로 스캔하는 정보**에만 쓴다. 서술에는 안 쓴다.

## 3. 우리 정체성 — 참고 글을 그대로 베끼지 않는 지점

참고 글은 **읽는 리듬**을 배울 대상이고, **SEO/GEO 체계는 우리가 세운다.**

| 항목 | 참고 글 | **우리 방식** | 이유 |
|---|---|---|---|
| 소제목 | 0개 | **섹션마다 `sectionTitle`** | 검색엔진 목차·AI 답변 인용의 근거. 없으면 GEO 를 포기하는 것 |
| 문단 길이 | 8~31자 | **25~40자** | 참고 글보다 약간 길게. 정보 밀도를 지키면서 호흡은 살린다 |
| 사진 밀도 | 100자/장 | **100자/장** | 그대로 따른다. 근거가 4편에서 일치한다 |
| 인용구 | 구조 대용 | **역할 고정** | 결론=`_line` / 팁=`_postit` / 인물·후기=`_bubble`. 독자가 모양으로 역할을 안다 |
| 한 줄 정리 | 없음 | **맨 위에 배치** | GEO 핵심. AI 가 인용할 한 문장을 글 맨 앞에 둔다 |
| FAQ | 없음 | **유지** | 롱테일 검색 유입 + AI 답변 인용 |
| 장소 | `placesMap` | **`placesMap` + 주소 표** | 지도(지역 SEO) 와 텍스트 주소(크롤링) 를 함께 |
| 스티커 | 3~6개 | **쓰지 않음** | 브랜드 톤과 안 맞고 정보 가치가 0 |

### 우리 글의 표준 순서 (호텔 + 근교 관광지)

```
대표 사진 (represent)
한 줄 정리            quotation_line   ← GEO: AI 가 인용할 한 문장
이 글의 핵심          sectionTitle + 가운뎃점 목록
─────────────────
[호텔]
  sectionTitle        "○○호텔 — 위치·객실·조식 한눈에"
  사진 → 짧은 글 → 사진 → 짧은 글 …
  quotation_postit    실제로 묵어 본 팁 / 주의
  표                  주소·체크인·요금·조식 시간
  placesMap           호텔 위치
─────────────────
[근교 관광지 N곳]  ← 호텔에서의 이동 시간을 반드시 함께 쓴다
  sectionTitle        "호텔에서 15분 — ○○"
  사진 → 짧은 글 → 사진 → 짧은 글 …
  quotation_bubble    현장에서 느낀 한마디
  표                  입장료·영업시간·소요 시간
  placesMap           관광지 위치
─────────────────
동선 정리             sectionTitle + 시간순 목록  ← "1일 코스" 검색 대응
예산 정리             sectionTitle + 표
자주 묻는 질문        sectionTitle + Q/A
마치며
─────────────────
참고 자료 · 이미지 출처
```

**호텔 + 근교를 엮는 것이 차별점이다.** 호텔 리뷰만 쓰는 글, 관광지만 쓰는 글은
넘친다. "이 호텔에 묶으면 근처에 뭐가 있나" 를 한 글에서 해결해 주는 것이
우리 글의 존재 이유다. → 관광지 섹션 제목에 **호텔로부터의 이동 시간**을 넣는다.

## 4. 기술 메모 — 실측으로만 알 수 있었던 것

### 제로폭 공백으로 여백을 만든다

문단 길이 분포에서 **최소·중간값이 1** 인 것의 정체는 빈 문단이 아니라
**제로폭 공백(`​`) 한 글자가 든 문단**이다.

> 빈 문단(`value: ''`)은 **발행하면 삭제된다** (실측: 발행된 글의 빈 문단 0개).
> 제로폭 공백을 넣으면 살아남아 한 줄 여백이 된다. 표본 6편이 모두 이 방법을 쓴다.

문단 사이를 띄우는 다른 방법은 전부 막혀 있었다:

| 시도 | 결과 |
|---|---|
| 빈 문단 | 발행 시 삭제 |
| 문단마다 컴포넌트 분리 | 인접 컴포넌트 간격 **0px** |
| 줄간격 `paragraphStyle.lineHeight` | **동작** (발행된 글에 `style="line-height:2.0;"`) |
| **제로폭 공백 문단** | **동작** (참고 글 6편이 모두 이 방법을 쓴다) |

### 참고 글의 타이포그래피

- 본문 15px 이 기본, 한 편만 19px(`se-fs-fs19`)
- 줄간격은 대부분 지정하지 않고(계산값 19.8px), 한 편만 `line-height:1.9`
- 즉 **줄간격보다 문단을 짧게 끊는 것이 본질**이다. 우리가 2.0 으로 올린 것은
  보조 수단이고, 문단 길이를 25~40자로 줄이는 것이 진짜 해결이다

## 7. `placesMap`(장소) — 진행 중 (2026-07-28)

### ⚠️ 해외 장소는 **'해외' 로 바꿔야 검색된다**

`장소` 버튼(`button.se-map-toolbar-button`)을 누르면 지도 레이어가 열린다.
검색창 **왼쪽에 `국내` / 해외 선택 드롭다운**이 있고 **기본값이 `국내`** 다.

> 2026-07-28 실측: 검색어 "도쿄돔시티" 를 넣었더니 **"검색 결과가 없습니다"**.
> 검색어가 틀린 게 아니라 필터가 `국내` 였다.

**"어디가지?" 는 전 세계를 다루므로 이게 치명적이다.** 이 드롭다운을 바꾸지 않으면
해외 글마다 장소가 조용히 0개가 되고, 실패 원인이 "검색어가 나쁘다" 로 오진된다.

→ 구현할 때 **국가/지역에 따라 국내·해외를 먼저 고른 뒤** 검색해야 한다.
   아티클에 '해외인가' 를 알려주는 값이 필요하다 (프롬프트에서 받거나 좌표로 판단).

### 레이어 구성 (실측)

| 요소 | 위치·역할 |
|---|---|
| 국내/해외 선택 | 검색창 왼쪽 드롭다운. **기본 `국내`** |
| 검색 입력 | 검색창. `Enter` 로 검색 |
| 결과 목록 | 왼쪽 패널 (없으면 "검색 결과가 없습니다") |
| `지도에 직접 표시` | 좌하단. 검색으로 안 잡히는 곳을 좌표로 찍는 폴백 |
| `확인` | 우하단. 선택을 확정해 본문에 삽입 |

### 다음 단계

1. 국내/해외 드롭다운의 셀렉터를 뜬다
2. '해외' 로 바꿔 다시 검색 → 결과 클릭 → `확인`
3. `getDocumentData()` 로 `placesMap` 컴포넌트 JSON 확보
4. 확보하면 `naverDoc.js` 에 `placesMap()` 빌더를 추가하고,
   호텔·관광지 섹션마다 하나씩 넣는다 (표본 jwsu73 은 5개)

⚠️ 사진 업로드처럼 **커서 위치에 삽입되는 컴포넌트**일 가능성이 크다.
그렇다면 사진과 마찬가지로 **본문 주입 전에 미리 삽입해 JSON 을 회수**하고,
조립 단계에서 원하는 자리에 끼우는 방식이 맞다 (naver.js 의 uploadImages 와 같은 전략).
